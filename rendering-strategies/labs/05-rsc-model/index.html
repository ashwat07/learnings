Lab 05 — The RSC model

Server Components are not "SSR with extra steps". The distinction that matters: a server component's code never reaches the browser at all. It runs once, on the server, and what crosses the wire is a description of its output — not the component, not its dependencies, not its data-fetching code.

The sandbox has a deliberately small model of the wire format (/render/rsc/ + shared/app/rsc-client.js). Read it before running anything — 40 lines, and it makes the shape obvious.

Start with "what crosses the wire".

the mental model

Server Component                        Client Component ("use client")
─────────────────                       ──────────────────────────────
runs on the server, once                runs on the server (SSR) AND in the browser
can await a database directly           cannot: no db, no secrets, no fs
its code is NEVER sent to the client    its code IS sent, and hydrated
cannot use state, effects, or events    can: useState, useEffect, onClick
zero KB of client JS                    costs bundle bytes + hydration time
can render client components            can only render server components passed as children

the boundary is one-way: once you are in a client component, everything you import
comes with you into the bundle. That is why "use client" at the top of a shared
utility file is the most expensive line of code in a lot of Next.js apps.
