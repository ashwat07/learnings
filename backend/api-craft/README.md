# API craft — build the service, make the tests pass ⭐⭐⭐⭐⭐⭐

The other shape. Where a database target is a number you can assert on, **API design is a set of
decisions** — so this course states them as a **failing test suite** and asks you to satisfy it.

```sh
cd backend
npm run up && npm run seed
npm run test:api                  # 25 tests, 22 failing. That is the exercise.
node --test --test-name-pattern="idempot" api-craft/test/
```

You edit **[`src/server.mjs`](src/server.mjs)**. The reference is in `src/server.reference.mjs` —
read it *after*.

## The contract

**The tests are the specification.** When a TODO is ambiguous, the assertion is the answer.

| Area | What's asserted |
|---|---|
| **health vs readiness** | `/healthz` is cheap; `/readyz` checks the DB **and reports not-ready once draining** |
| **listing** | `{data, nextCursor}`; two pages of 10 equal one page of 20; ten pages deep still works |
| **pagination** | **keyset, not OFFSET** — and a malformed cursor is a 400, not a 500 |
| **validation** | per-field `details`; unknown enum values rejected; malformed JSON is a 400 |
| **resources** | 404 for a missing id, **400 for a non-numeric one** |
| **creation** | 201 with a `Location` header; `status` defaults to `pending` |
| **idempotency** | a replayed key returns the **original** order; a different body is a **409**; **8 concurrent retries create exactly one order** |
| **cross-cutting** | one error envelope everywhere; `x-request-id` on every response, **echoed** if inbound; an internal error **never leaks the exception** |

## The five that carry the most weight

**1. Readiness must fail *before* you stop accepting connections.** A draining instance that still
reports ready keeps receiving traffic it's about to refuse. That's why "graceful" deploys still drop
requests — the fix is to flip readiness, *wait for the load balancer to notice*, and only then close.

**2. One error envelope, for everything.** Including 404s and framework errors. Clients write one
handler or they write none.

**3. User input must never produce a 500.** A malformed cursor, a non-numeric id, truncated JSON —
all 400. A 500 means *you* have a bug; using it for *their* mistake makes your alerts useless.

**4. Idempotency is a transaction, not a lookup.** The `SELECT`-then-`INSERT` version passes a
sequential test and fails the concurrent one. The atomic claim is:

```sql
INSERT INTO idempotency_keys (key, ...) VALUES (...)
ON CONFLICT (key) DO NOTHING RETURNING key   -- exactly one winner
```

The key and the order must be written in **one** transaction — the same argument as
[the outbox drill](../caching-and-queues/drills/04-the-outbox/).

**5. Never return the exception.** The test throws
`SELECT * FROM secret_table failed at /srv/app/db.js:42` and asserts neither the table name nor the
path appears in the response. Log the real error with the request id; return a generic message and
that id.

## Keyset pagination

```sql
WHERE (created_at, id) < ($cursor_created_at, $cursor_id)
ORDER BY created_at DESC, id DESC
LIMIT $limit + 1        -- the extra row tells you whether there IS a next page
```

`LIMIT n+1` is the trick that avoids a second `count(*)`. And the tiebreaker (`id`) isn't optional —
without it, rows sharing a timestamp get skipped. Measured in
[postgres lab 08](../postgres/labs/08-n-plus-1-and-orms/).

## Think about

- Why can't `/healthz` and `/readyz` be the same endpoint?
- A client retries a POST after a timeout. What must be true?
- Why is a 500 for bad user input actively harmful?

<details>
<summary>Answers</summary>

**Health vs readiness.** *Liveness* asks "is this process broken — should you kill it?"; *readiness*
asks "should you send it traffic right now?". They differ during startup (alive, not ready),
draining (alive, not ready), and dependency loss (ready should fail; killing the process wouldn't
help). Conflating them means either restart loops during a slow start, or dropped requests during a
deploy.

**Retried POST after a timeout.** The request may have *succeeded* — a timeout tells you nothing
about the server. So the retry must carry the **same idempotency key** the first attempt used,
generated by the client before the first send and persisted with the pending operation. The server
must store the key and the response in the same transaction as the effect. See
[resilience lab 02](../../resilience/labs/02-retries-and-idempotency/).

**500 for bad input.** It corrupts your signal. A 5xx rate is the thing you alert on and page for;
if a user typo generates one, either your alerts fire constantly and get muted, or the threshold is
raised until real failures hide beneath it. 4xx says "the client did something wrong"; 5xx says "we
did". Keeping them honest is what makes either number worth watching.
</details>

## 🏗️ Build challenge

Once the suite is green, extend it — write the test **first**:

1. `PATCH /orders/:id` with optimistic concurrency: `If-Match` an ETag, **412** on mismatch
   ([postgres lab 06](../postgres/labs/06-transactions-and-locking/)).
2. Idempotency-key **expiry**, and a test that an expired key allows a new order.
3. Rate limiting per API key, returning `429` with `Retry-After`
   ([caching drill 02](../caching-and-queues/drills/02-the-rate-limiter/)).
4. An OpenAPI document generated from the same zod schemas, and a test that every route appears.
5. Real graceful shutdown: SIGTERM → readiness false → wait → `close()` → drain → exit, with a hard
   timeout. Test it by sending SIGTERM mid-request and asserting the response still arrives.
6. Structured logs with the request id, and a test that no log line contains a password or token.

**Done when:** `npm run test:api` is green and you've added at least two tests of your own.
