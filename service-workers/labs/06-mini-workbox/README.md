## Why a router

A service worker's job isn't "caching". It's **a policy per kind of request**, and the policy is
the thing your team needs to be able to read and argue about:

```js
registerRoute(r => r.mode === 'navigate',                 Navigation({ fallback: './offline.html' }));
registerRoute(u => u.pathname.startsWith('/assets/'),     CacheFirst({ cacheName: 'static' }));
registerRoute(u => u.pathname === '/api/image.svg',       CacheFirst({ plugins: [expiration({maxEntries: 60})] }));
registerRoute(u => u.pathname.startsWith('/api/feed'),    StaleWhileRevalidate());
registerRoute(u => u.pathname.startsWith('/api/'),        NetworkFirst({ networkTimeoutMs: 1200 }));
registerRoute(u => u.pathname.startsWith('/api/cart'),    NetworkOnly());
```

That block is the deliverable. It's the same artefact as the header policy in the HTTP caching
course, expressed in code instead of headers — and it's what a reviewer should be able to check
without reading a single strategy implementation.

## What's written for you

- The **router**, including the thing that matters most: every strategy is wrapped in
  `.catch(() => fetch(request))`, so a bug degrades to "no caching", never to "the site is down".
- **CacheFirst** and **NetworkOnly**.
- Two plugins: `cacheableResponse` (keep opaque 404s out) and `timestamp` (make expiry possible).
- A **test suite** on the page that asserts which strategy answered and how it behaved.

## Your five TODOs

**TODO 1 — `expiration({ maxEntries, maxAgeMs })`**
Hooks: `cachedResponseWillBeUsed` (return `null` to force a miss) and `cacheDidUpdate` (enforce
the entry cap). Age comes from the `x-cached-at` header the `timestamp` plugin writes.
The hard part is **LRU, not FIFO**: `cache.keys()` gives you insertion order only, so you need a
side index of last-used times, and you need to decide what happens when the worker is killed
between updating the cache and updating the index. Write down which inconsistency you chose and
why it's the recoverable one.

**TODO 2 — `NetworkFirst({ networkTimeoutMs })`**
Lab 03. Race the network against a timeout, fall back to cache, let the slow request finish
anyway, synthesise a useful error when there's nothing.

**TODO 3 — `StaleWhileRevalidate()`**
Lab 04. Return cached immediately, refresh in the background, **coalesce** concurrent refreshes
(one of the tests checks the server hit count), and bound how stale is too stale.

**TODO 4 — `NavigationStrategy`**
Try `event.preloadResponse`, then the network, then the cached page, then `./offline.html`.

**TODO 5 — activate**
Enable navigation preload, and delete versioned caches that aren't the current version. Note the
`images` and `api` caches are deliberately *unversioned* — work out why before you delete them.
(Hint: what would happen to a user's 60 cached images on every deploy?)

## The tests

| Test | What it proves |
|---|---|
| static → CacheFirst | routing works, cache hit is < 50ms |
| images → expiration | TODO 1 |
| fresh API → NetworkFirst | TODO 2 — a 3s server answers in ~1.2s |
| swr API → SWR | TODO 3 |
| 10 concurrent SWR reads | TODO 3's coalescing — ≤ 1 server hit |
| never-cache → NetworkOnly | 2 reads = 2 server hits |
| a throwing strategy | **the fallback works even when everything else is broken** |

The last one is the point. Get it passing first (it already does), and never break it.

## Extending it — the parts that make it real

Once the seven pass, add:

1. **A precache manifest** generated by a build step, with revision-aware updates (Lab 02's build
   challenge). This is where most of Workbox's actual value lives.
2. **`broadcastUpdate`** — a plugin that posts a message to clients when a SWR refresh produced
   *different* bytes, so the UI can say "new content available" instead of silently changing
   under the user's cursor. Compare by `ETag`/`Last-Modified`/`Content-Length`, and document what
   your comparison misses.
3. **Range request support** — either pass them through (correct default) or implement real 206
   slicing.
4. **The kill switch and error reporting** from Lab 05. Not optional.
5. **A `debug` mode** that logs every routing decision with the matched rule, so "why did this
   request get cached?" is a five-second question.

## When to use Workbox instead

You've now built the thing, so you can answer this properly. Use the real library when you need
its precache manifest tooling and build integration — that's genuinely hard to get right (revision
diffing, cache-busting on install, integrity). Write your own when your policy is small enough to
read on one screen and you'd rather own 200 lines than a dependency and its abstractions.

What you should *never* do again is write ad-hoc `if (url.includes('/api/'))` logic directly in a
fetch handler. That's the version that becomes unreviewable in three sprints.

## 🏗️ The final build challenge: ship it, break it, recover it

Take your mini-Workbox and put it in front of a real (small) app of yours. Then run an exercise:

1. **Ship v1.** Verify: offline works, LCP on repeat visit, cache sizes bounded.
2. **Ship v2 with a deliberate bug** — a strategy that caches a 500 as if it were content.
3. **Observe it as a user would**, on a second device or profile. How long until you notice?
   What does your monitoring say? Do you know how many users are on v2?
4. **Recover** using only the kill switch. Time it.
5. **Write the post-mortem**: what would have caught this before it shipped, what monitoring was
   missing, what you'd change about the release process.

Deliverables: the routing table, the incident timeline, and one paragraph on what you'd do
differently. That last paragraph is what separates someone who has used a service worker from
someone you'd let ship one.

## Interview questions

1. Why is a routing layer better than `if`s in a fetch handler?
2. What's the one thing you'd implement first in any service worker, before any strategy?
3. Design the strategy for each of: the app shell, product images, the user's cart, a public feed,
   an analytics beacon, a 40MB video.
4. Why version some caches and not others?
5. How would you implement LRU eviction over Cache Storage, and where does it go wrong?
6. When would you use Workbox instead of your own, and what specifically is it buying you?
