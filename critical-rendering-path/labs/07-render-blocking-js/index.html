Lab 07 — JavaScript blocking rendering

Five pages, identical content and identical total work. Open each in a fresh incognito tab with Network: Fast 3G and CPU: 4×, and reload-and-record.

Must be served over HTTP — use ./serve.sh from the course root. Opening these with file:// gives you misleading resource timings.

  • 01 · synchronous script in <head> — 800ms of blocking work before any DOM exists. Count the white-screen seconds.
  • 02 · same script, before </body> — content paints first, then the freeze. Better FCP; is it a better experience?
  • 03 · defer — parses without pausing, executes in order before DOMContentLoaded.
  • 04 · async, with a dependency — reload it several times. Sometimes it works, sometimes it throws. Find out why.
  • 05 · your fix — you build this one. Same work, FCP < 1s, no long tasks, page interactive during load.

Also try

  • In any page, comment out scripts/heavy.js and uncomment scripts/slow-download.js — that swaps slow-to-execute for slow-to-download. Throttle the network and compare. Predict which case the preload scanner can hide before you measure.
  • In 01, uncomment the slow.css link that sits before the script, and watch script execution wait for a stylesheet.

Each page prints its own FP/FCP/LCP/DCL and an execution-order log, on the page and in the console. Write the numbers into README.md as you go.
